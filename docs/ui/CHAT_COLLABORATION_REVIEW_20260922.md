# Zeus 会话协作体验与改进建议（2026-09-22）

## 结论

建议把人与人、人与 Agent、Agent 与 Agent 纳入同一套组织会话。Agent Studio 与 IM Studio 可以暂时保留为不同视图，但应共享会话列表、成员模型、消息、通知和业务关联。最终客户端以聊天为首页，Business Studio 继续管理工作项、可复用流程、Run、审批与经验，Management Terminal 管理身份、权限、模型和工具。

本次登录 3000 的 E2EAdmin 账号，实际导航并检查新会话、组织群聊和审批中心；未发送真实团队消息、未批准业务操作、未修改实现。截图为本次采集，历史消息仅用于观察当前呈现。代码检查补充了成员模型、同步方式与权限规则的证据。

## 当前体验：三个步骤

### 1. Agent Studio 新会话：基础入口清楚，协作入口缺失

![Agent Studio](../../.zeus/evidence/chat-audit-20260922/01-agent-studio.png)

- 好处：聊天优先，输入框清楚，创建工作默认先预览。
- 问题：没有显示当前对话 Agent 的身份、职责和权限，也没有选择 Agent、邀请同事、邀请另一个 Agent 的入口。与 IM 使用两套会话区域。
- 改进：新会话先选择人或 Agent；顶部展示成员；加入人或 Agent 使用同一个参与者入口。已有聊天保持历史和关联工作，不因添加成员创建一套无关 Run。

### 2. IM 群聊：基础交流可见，尚不能承载人机协作

![IM 群聊](../../.zeus/evidence/chat-audit-20260922/02-group-chat.png)

- 好处：组织、成员、发送者、引用回复和未读都有明确呈现。
- 问题：提及通过单选下拉完成；输入中没有自然的 @ 选择体验。侧栏长期占据空间，消息正文区域偏窄。消息操作没有请求审批、转工作项、交给 Agent 的入口。
- 当前 im_members.user_id 与 im_messages.sender_id 指向用户，不能把现有 Agent 直接作为独立会话成员。不能仅把 Agent 名字画成头像就宣称支持多 Agent。
- 改进：输入 @ 搜索当前组织的人和已授权 Agent；群成员面板按需展开；消息支持引用到线程、转任务和发起审批。外部组织身份持续展示，本期先保持组织内。

### 3. 审批中心：授权边界清楚，聊天到审批没有闭环

![审批中心](../../.zeus/evidence/chat-audit-20260922/03-approvals.png)

- 好处：区分发起人执行确认、Workspace Owner 资源授权以及业务结果验收。
- 问题：群聊无法在原消息上下文里发起、处理和追踪审批；当前页面无待处理记录，因此本次没有验证实际审批提交。
- 当前资源审批仍是 Workspace Owner 策略；没有通用汇报线/直属领导目录。领导头衔不能自动代替资源授权资格。
- 改进：聊天显示同一审批实体的卡片，包含申请人、目标、范围、期限、待谁处理、批准/拒绝及审计链接。聊天“同意”不能由模型直接解释成有效授权。

## 产品结构建议

统一 Conversation，成员明确区分 human 与 agent；Agent 配置版本和实际参与会话的 Agent 身份分开。组织提供可用 Agent 目录，配置职责、所属人、模型、工具范围、费用上限和响应方式，用户可从已有模板创建。一个 Agent 可以参与多个会话，但默认隔离会话上下文。

聊天记录属于 Conversation；执行证据仍属于原有 WorkItem/Workflow/Run/Approval/Session Event。Conversation 引用业务实体，一个会话可关联多个工作项，一个工作项也可在多个获授权会话讨论。不得把多人聊天直接塞进一个共享模型 Session，导致所有 Agent 继承同一权限。

会话可以不绑定 Workspace；真正启动工作时明确选择目标 Workspace，由后端检查发起人的权限。加入群聊不会授予资源访问权。领导加入 AI 私聊时提供“仅后续内容 / 分享摘要 / 指定历史”选择，分享摘要也要可预览；成员列表显示实际可见范围。

建议客户端导航：收件箱（未读、@我、待审批）→ 会话（人/Agent/群组）→ Agent 目录 → 我的工作。现有四模块可作为网页入口和管理分区保留，避免重复建设两套聊天协议。

## @、任务和审批

- @同事：提醒和协作，不自动修改负责人或授权。
- 领导@成员交办：从该消息提出工作项草稿，显示负责人、期限和验收标准，确认后创建；普通聊天不必全部变为任务。
- @Agent：确定被调用的 Agent；需要执行时建立 Run 并关联回原消息。
- 发起审批：结构化申请，后端按申请类别解析合法审批人。直属领导可负责业务决定，资源负责人负责访问许可；两者不必是同一人。
- 发起人执行确认、上级业务审批、资源访问授权和结果验收分别记录，界面用简单文案区分。

示例：员工与需求 Agent 讨论方案 → 邀请领导并分享选定摘要 → 领导在原线程提出约束 → Agent 给出工作项草稿 → 员工确认 → 遇到受限资源生成资源授权卡 → 合法负责人批准 → 必要时发起人确认执行 → Run 恢复 → 结果回到线程，进入人工验收。

## AI 何时参与

先提供三种明确模式：仅被 @ 时回复（默认）；对话内授权的主动建议；授权任务范围内的执行。

“主动建议”只面向已加入且获准观察的 Agent。识别到待办、重复问题或需要整理时先提供轻量建议；不得扫描未加入的群、自动扩大成员权限或强行插话。未加入 Agent 的会话可提供手动“请 AI 帮忙”，不能声称 AI 在不读取内容的情况下判断何时加入。

多 Agent 使用一个可见协调者按任务分工，限制回合、费用、并发和超时，保留因果链和去重。避免 Agent 之间每条回复触发新回复。常规交接折叠展示，用户可查看参与者和各自成果；暂停、停止和等待人工决定应明确可见。

## 实时消息与通知

代码当前每 3 秒 invalidateAll，document.hidden 时跳过；未找到 Notifications API、PushManager 或 service worker 通知实现。因此“自动同步”不代表后台通知已具备。

1. 在线：POST 持久写入 + SSE（或有实际双向需求再选 WebSocket），以消息游标补发、去重、重连；不要把全页轮询当长期消息传输。
2. 提醒：服务端保存通知收件箱，分类为私信、@我、审批、任务结果；Web Notifications 展示系统提醒。
3. 页面关闭：Web Push + Service Worker + 用户授权 + 生产 HTTPS。投递受浏览器/系统策略影响，不承诺绝对即时。权限被拒绝时仍可从未读与待办恢复工作。
4. 客户端：复用相同会话、通知和执行 API，增加原生通知、托盘、深链接及离线恢复；服务端运行不依赖客户端在线。实现多设备去重、已读同步、免打扰和敏感内容预览设置。

## 实施次序与验收

| 顺序 | 范围 | 验收标准 |
|---|---|---|
| P0 | 统一会话和人/Agent 成员 | 一个会话包含两个用户和一个 Agent；@对象准确；分享历史受控；组织与 Workspace 权限不混用 |
| P0 | 单 Agent 群聊与任务关联 | 聊天生成草稿，确认建立 WorkItem；执行结果回原线程；原有聊天仍可访问 |
| P0 | 审批卡与负责人规则 | @提醒不授权；合法审批人才能决定；挂起后恢复；参数变更使旧授权失效 |
| P1 | 实时事件、收件箱与 Web Push | 两个独立浏览器持续在线；断线补发不重复；隐藏/关闭页面测试；拒绝通知权限仍能找回待办 |
| P1 | 多 Agent 协作 | 两个 Agent 完成明确分工，费用与回合有限；成员不能越权委派；可暂停停止并追踪结果 |
| P2 | 独立客户端 | 与 Web 会话一致；跨端未读和审批一致；退出客户端不终止服务端任务 |

优先完整交付“两个人 + 一个 Agent + 一次真实审批 + 一个结果”，再扩大自主协作和客户端范围。
